System Architecture

Browser Dashboard
HTML · JS · Chart.js — served from ESP32 LittleFS
Single-page app: Dashboard, Analytics, Logs, Schedules, Settings
WebSocket client — subscribes to live power:update, relay:update, logs:new
Polling fallback (every 2 s) if WebSocket drops, with exponential backoff reconnect
Session token stored in localStorage — validated server-side on every request
Node.js Backend
Express · ws · mysql2 · bcrypt — port 3000
REST API under /api/* — handles relays, schedules, energy, users, notifications
WebSocket hub (wsHub.js) broadcasts to frontend clients AND ESP32 on the same socket server
Schedule runner fires every 60 s — reads findDueNow() and calls RelayService.setState()
Alert engine checks overload thresholds after every sensor reading; generates notifications
MySQL Database
MariaDB / XAMPP — breaksmart schema
Tables: devices, relays, sensor_readings, energy_snapshots, schedules, activity_logs, notifications, users
Schedule days stored as a bitmask (bitfield) — decoded to an array by the API layer
Energy analytics use aggregated views — daily/weekly/monthly group-by queries
Session tokens hashed and stored with expiry; bcrypt for passwords (12 rounds)
ESP32 Firmware
Arduino · LittleFS · WebSocket client — port 80
Serves the browser dashboard from LittleFS flash filesystem (index.html, script.js, Chart.js)
Controls 4 relay GPIO pins (19, 18, 5, 17) — active-LOW relay boards supported
4× ACS712 current sensors on ADC pins (GPIO 34/35/32/33) — sends esp32:reading every 10 s
Sends esp32:heartbeat every 25 s to keep device online status in DB
Displays real-time data on 20×4 I²C LCD (SDA GPIO21, SCL GPIO22)
AC Power Chain
Wall plug → MCB → 4 relay channels → load sockets · HLK-5M05 powers ESP32 (5V DC)
CH1: Relay1 → ACS712 #1 → Socket1
CH2: Relay2 → ACS712 #2 → Socket2
CH3: Relay3 → ACS712 #3 → Socket3
CH4: Relay4 → ACS712 #4 → Socket4
Real-Time Protocol

WebSocket Events

Backend → Frontend
relay:update
Fires whenever a relay is toggled ON or OFF. Carries relay_id, is_on, name. Triggers optimistic UI revert if mismatch.
Backend → Frontend
power:update
Sent after every ESP32 sensor reading. Contains voltage, current, power_w, energy_kwh, load_pct per relay. Updates the live gauge and stat cards.
Backend → Frontend
logs:new
Pushed whenever a new activity log entry is created — relay toggles, schedule executions, overload alerts. Updates Logs page in real time without polling.
Backend → Frontend
device:status
Sent when a heartbeat is received (online) or when the ESP32 WebSocket connection drops (offline). Drives the connectivity indicator in the UI.
Backend → Frontend
notification:new
Triggered when the alert engine generates a new notification — overload, relay trip, energy limit exceeded. Increments the bell badge counter.
Backend → Frontend
dashboard:summary
Re-broadcast after every relay toggle — carries aggregated active_relays count and total_power_w for the dashboard stat bar.
ESP32 → Backend
esp32:reading
ESP32 sends sensor data every 10 seconds. Backend saves to sensor_readings table, runs alert checks, then re-emits as power:update to all frontends.
ESP32 → Backend
esp32:heartbeat
Periodic keep-alive every 25 s. Backend updates is_online = 1 and last_seen_at in the devices table; missing heartbeats trigger connectivity alerts.
ESP32 → Backend (ACK)
esp32:relay_ack
Confirmation after the ESP32 physically actuates a GPIO pin. Backend re-broadcasts the confirmed state to frontends, completing the full round-trip.
Panelist Preparation

Anticipated Questions

BreakSmart is a smart circuit breaker monitoring and control system. It solves the problem of not being able to remotely manage, monitor, or automate the electrical circuits in a building. Instead of manually toggling breakers, users can control 4 relay channels (outlet circuits) from any web browser on the local network, view real-time power consumption, set automated schedules, and receive alerts — all without cloud dependency.
The ESP32 microcontroller serves a browser dashboard and physically controls 4 electrical relays and reads current sensors. A Node.js backend server running on a PC handles the logic, stores data in MySQL, and acts as a message broker using WebSocket. The browser talks to Node.js via REST API and WebSocket. Node.js then sends commands to the ESP32 over WebSocket to actuate hardware in real time.
No. BreakSmart is fully offline-capable after initial setup. The ESP32 serves the entire dashboard (HTML, JavaScript, Chart.js) from its own flash filesystem over your local Wi-Fi. The Node.js backend and MySQL database run on a local PC. Internet is only needed during initial setup to download Node.js, XAMPP, and libraries — never at runtime.
The dashboard has several pages: a main Dashboard with live power stats and a gauge, an Outlet Control page with 4 relay cards (toggle buttons, rename, schedule), an Analytics page with energy bar/line charts, a Logs page with the activity history, a Notifications panel, and a Settings page for thresholds and user preferences.
The core hardware is an ESP32 development board, a 4-channel relay module (active-LOW), 4× ACS712 current sensors, an HLK-5M05 AC-to-DC converter for powering the ESP32, a standard MCB (miniature circuit breaker), and a 20×4 I²C LCD display. All components connect to the ESP32 GPIOs — relays on GPIO 19/18/5/17, sensors on ADC pins 34/35/32/33, and LCD on I²C pins GPIO21/22.
Default admin credentials after running the setup script are: Email: admin@breaksmart.io, Password: breaksmart2024. The session is stored in localStorage and validated server-side on every API request. Sessions expire after 7 days.
(1) User clicks the toggle in the browser — the UI updates optimistically. (2) script.js sends PATCH /api/relays/:id/state to Node.js. (3) Node.js calls RelayService.setState() which updates the DB and emits relay:update over WebSocket to all frontends AND relay:command to the ESP32. (4) ESP32 actuates the GPIO pin and sends esp32:relay_ack back to Node.js. (5) Node.js re-broadcasts the confirmed state to all frontends. If the backend call fails, the optimistic UI update is reverted.
Schedules are stored in MySQL with time, action (on/off), and a day-of-week bitmask. The Node.js server runs a schedule checker every 60 seconds, aligned to the minute boundary. It calls ScheduleModel.findDueNow() which queries for enabled schedules matching the current time and day. Due schedules are executed via RelayService.setState() — the same path as manual toggles, ensuring WebSocket broadcast and DB update. The ESP32 also polls GET /api/schedules/due every 60 s as a hardware-level fallback in case the WebSocket is disconnected.
The ESP32 sends esp32:reading events every 10 seconds with current and power data per relay. On the backend, alertEngine.js checks the incoming readings against the device's max_load_w and alert_threshold_pct thresholds stored in device_thresholds. If a threshold is breached, the alert engine creates a notification record in MySQL and emits a notification:new WebSocket event so the browser badge updates immediately. A daily energy report also fires at midnight.
The frontend detects the WebSocket close event and automatically falls back to HTTP polling every 2 seconds (POLL_MS = 2000). It polls the relay states, latest readings, and activity logs via REST API. Simultaneously, it attempts to reconnect to the WebSocket with exponential backoff. The ESP32 also detects WebSocket disconnect and independently falls back to polling /api/schedules/due to ensure schedules still fire on hardware. The Node.js server is configured with keepAliveTimeout of 65 s and a 2-minute socket timeout to prevent premature TCP resets.
Each of the 4 relay channels has an ACS712 current sensor wired in series with the load. The ESP32 reads the analog voltage from the ACS712 on ADC pins (GPIO 34, 35, 32, 33). The ACS712 outputs a voltage proportional to current; the ESP32 calculates RMS current, then derives power (W) assuming a known AC voltage and power factor. Energy (kWh) is calculated by integrating power over time. These values are sent as esp32:reading WebSocket events, stored in sensor_readings, and aggregated into energy_snapshots for charting.
The backend follows a layered architecture: Controllers (HTTP handlers) → Services (business logic) → Models (raw DB queries). Services are responsible for both executing the business logic AND emitting WebSocket events after every state change. For example, relayService.setState() updates the DB, logs the activity, emits relay:update and dashboard:summary via the WebSocket hub. This means real-time updates are guaranteed regardless of whether a toggle comes from a user, a schedule, or the /logRelay legacy shim.
wsHub.js uses the native Node.js ws library and attaches to the same http.createServer() instance as Express, so both REST and WebSocket share port 3000. The hub maintains a Set of connected clients tagged by type (frontend vs esp32). Broadcast helpers like emitRelayUpdate() iterate the Set and serialise JSON. The ESP32 identifies itself by sending a { "event": "esp32:identify", "device_id": 1 } message on connect, so targeted commands (like relay:command) are only sent to the ESP32 client, not all frontends.
Schedule days (Mon–Sun) are stored as a 7-bit integer bitmask in a single TINYINT column. Bit 0 = Monday, Bit 6 = Sunday. This makes the "due now" query efficient — a bitwise AND against the current day-of-week bit is executed directly in MySQL: days_bitmask & (1 << weekday) != 0. It avoids a separate junction table and makes the query O(1) on an indexed column. The API layer in ScheduleModel.js decodes the bitmask back to an array of day strings for the frontend.
An early design bug caused double relay commands (once from the schedule runner via WebSocket, and once via a separate wsHub.emitRelayCommand() call). The fix was to route ALL schedule executions exclusively through RelayService.setState(), which internally calls emitRelayUpdate() — which in turn sends relay:command to the ESP32. The schedule runner no longer calls any WebSocket function directly. Additionally, the HTTP server's keepAliveTimeout is set to 65 s and headersTimeout to 70 s to prevent NAT router TCP resets from being misinterpreted as WebSocket closes by the ESP32.
Older ESP32 firmware versions used a simpler HTTP POST to /logRelay instead of WebSocket events. The compatibility shim at server.js catches these legacy calls, updates the DB, and re-broadcasts via the WebSocket hub — so older firmware units still work without rewriting the ESP32 sketch. The shim maps the legacy { relay, state } payload to the normalised relay update event, ensuring all connected frontends receive real-time updates even from legacy hardware.
The schema already includes a device_id foreign key on every table — relay, reading, log, and schedule rows are all device-scoped. The WebSocket hub tags each connected ESP32 by device_id, so relay:command events are routed only to the correct device. Scaling to additional units requires: (1) inserting a new row in the devices table, (2) flashing a new ESP32 with the correct DEVICE_ID, (3) no backend code changes. For horizontal scaling beyond a single Node process, the WebSocket hub would need to be extracted into a Redis pub/sub adapter to share state across multiple Node instances.
Security layers include: (1) Helmet.js sets HTTP security headers (XSS protection, content-type sniffing prevention). (2) Passwords are bcrypt-hashed with cost factor 12. (3) Session tokens are UUIDs stored hashed in MySQL with a 7-day expiry — validated on every API request via the X-Session-Token header. (4) CORS is configurable — in production, CORS_ORIGIN should be set to the ESP32's IP to restrict API access. (5) express-validator sanitizes and validates all incoming request bodies. In a production deployment, WS and HTTP should be behind HTTPS/WSS, and the MySQL user should be restricted to the breaksmart database only.
